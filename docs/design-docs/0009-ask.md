# ADR 0009 — Ask the archive: questions in plain words, answered with SQL

Status: **accepted** (2026-10-07), partly superseded by [0010-one-api.md](0010-one-api.md): the
pipeline and the question log move into one API service, with DuckDB on the server. Epic `swr-ei6`. Spec:
[explore.md](../product-specs/explore.md).

## Context

Explore answered questions only in SQL, which most visitors don't write. The owner wanted plain
questions. Two ways were weighed: question templates with fill-in blanks, and an AI model that
turns a question into SQL. The owner chose the model, through an OpenAI-compatible endpoint
they provide.

## Decision

1. **The model writes SQL; the server runs it.** A question goes through five steps
   (`src/domain/ask.ts` has the prompts and checks, `src/domain/ask-pipeline.ts` runs them, and
   the API in `src/server/` serves them as a stream of events; ADR 0010):
   1. **Plan:** the model lists the proper names in the question.
   2. **Resolve:** each name goes through the search title index (`swr-357`, [search.md](../product-specs/search.md)), which
      knows redirects: "the Rebel Alliance" becomes "Alliance to Restore the Republic". Models
      guess exact titles badly; this step mattered more to accuracy than any prompt change.
   3. **Write SQL:** the model gets the three tables, each section's commonest kinds and fields
      (`ask-schema.json`, written by the build beside the database), worked examples, and
      the resolved titles. It answers in JSON.
   4. **Check and run:** one `SELECT` or `WITH`, balanced parentheses, capped at 200 rows (one
      more is fetched to know if there were more). DuckDB runs it on the server, on the
      read-only database. A failure goes back to the model with its error, up to three tries in all.
   5. **Summarize:** one or two sentences, streamed, written only from the rows. The rows and
      the query are shown too, so a reader can check the sentence.
2. **The browser never holds the key.** The endpoint sends no CORS headers, so a page can't
   call it directly; and a key in the bundle would be anyone's. The browser posts only the
   question (and its history) to this site's `/api/ask`; the API calls the model with the key
   from its environment (`ASK_ORIGIN`, `ASK_KEY`). The dev and preview servers run the same API
   in-process, from `.env`. The body is capped at 64 KB, answers are `no-store`, and the CSP
   keeps `connect-src 'self'`.
3. **The model is configurable:** `ASK_MODEL`, read by the API at start. It talks to the
   endpoint with plain `fetch`; no SDK.
4. **No rate limit**, by the owner's choice. The server can add one later without touching the
   browser.

## The question log (`swr-ca3.3`)

Every question is recorded, so the prompts can be improved from what people ask: one row in a
DuckDB table (`questions`: when, the question, its outcome, the names it matched, the SQL, the
row count, the seconds it took, the model, and whether it followed earlier questions). Nothing
identifies the visitor: no IP, no user ID, no cookie. The API writes the row when a question ends (`src/server/questions.ts`), to
`questions.duckdb` on a volume, in a DuckDB instance of its own that visitors' SQL can't reach
(ADR 0010). The dev and preview servers write to `data/questions/` instead. Mine it with the
DuckDB CLI, and `ATTACH` the archive to join the two:
`SELECT outcome, count(*) FROM questions GROUP BY 1`.

## Measured (2026-10-07, the full archive)

`pnpm ask:eval` (`test/fixtures/ask-eval.json`, run on request, never in the gate) asks 30
questions through the real pipeline and checks each query's rows, and for some the first 10.
First run: 25 of 30; after fixing what it found (ordering lists by `links`, best known first;
"who" means characters; the direction of facts, with an example; works by a person): 29 of 30.
The miss: "Who flew the Millennium Falcon?" (the model reads its captains, not its owners).

Earlier, by hand: thirty test questions against the real model: about 26 answered correctly, typically in 5 to 9
seconds (outliers to 40 when the endpoint was slow). The misses were questions the data can't
answer the way they're asked (the ships Han Solo owned: those facts sit on the ships, under
fields the model didn't pick) and loose kinds ("Star Destroyers" lists all Imperial ships).

## Consequences

- Answers can be wrong. The page shows its working (names matched, the query, the rows), so a
  wrong answer is visible, and the SQL editor is one click away.
- Questions leave the site for the AI service; the page says so under the box.
- The smoke test stubs the model (fast, free, the same every run). Prompt quality is checked
  by hand against real questions: rerun them after changing a prompt.
